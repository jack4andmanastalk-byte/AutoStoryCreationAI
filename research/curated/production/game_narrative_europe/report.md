# 現代ヨーロッパのゲーム開発における物語・キャラクター・世界観・歴史構築
## パイプライン、PDCA、プロダクト開発イテレーションの調査・実務カタログ

**調査基準日：2026年10月23日**  
**対象：** 欧州を中心とした商業ゲーム開発と関連する学術研究。物語／ナラティブ、キャラクター、世界設定、歴史表象を、企画から発売後までの制作プロセスに位置づける。  
**付属データ：** [`european_game_narrative_sources.jsonl`](european_game_narrative_sources.jsonl)（情報源メタデータ、21レコード）

## 1. 要約

本調査で最も重要な結論は、**「ヨーロッパのゲーム開発には一つの標準ナラティブ・パイプライン／統一PDCAがある」とは言えない**ことである。ゲーム制作の実証研究は、ジャンル、規模、組織、契約、技術、プロジェクトごとの違いを強調する。ゲームでは「面白さ」「理解される物語」「プレイヤーの選択が感じられること」などが制作中に初めて検証できるため、開始時に全仕様を確定する予測型計画は難しい。反対に、柔軟性だけに頼ると、物語の遅れ、役割の曖昧さ、レベルやアートの手戻り、スコープ肥大が起こる。したがって現実的な答えは、**固定する核（体験の約束、テーマ、ゲームの前提）と、検証に応じて変更する部分（個別シーン、クエスト、台詞、表現、実装）を分け、複数の時間尺度で反復すること**である。[S01–S05]

実務上は、次の「二重ループ」が有効な統合モデルとなる。

1. **大きな製品ループ（ステージ／マイルストーン）：** 企画・コンセプト → プリプロダクション → 縦切りスライス／制作準備 → 本制作 → アルファ／ベータ・認証 → 発売 → ライブ運営・拡張。
2. **小さな学習ループ（機能／コンテンツ単位）：** 仮説を決める → 素早く試作・実装する → プレイ観察・専門レビュー・品質確認 → 結果を解釈する → 採用／修正／縮小／撤回 → 仕様・バックログ・計画へ反映する。

この小ループをPDCAに対応させると、**Plan＝検証したい体験・ナラティブ仮説と成功条件の定義、Do＝プロトタイプ／実装、Check＝プレイヤーの行動・理解・感情・技術品質・史実検証の確認、Act＝修正・スコープ変更・学びの記録**となる。ただし、これは研究結果を実務に翻訳した運用案であり、欧州各社が「PDCA」という名称で統一的に実践しているという意味ではない。研究上も「Agile」はしばしば、厳密な方法論というより柔軟な制作の総称として使われる。[S01–S04]

物語／世界構築を他部門の後工程に置くのではなく、**コンセプト時点からゲームデザイン、レベル、アート、音響、実装、UX、QAと接続する**のが要点である。ナラティブが遅れて固まると、レベルの再設計・破棄や作業停止に波及するというスタジオ観察が報告されている。[S05] その一方で、最初に書いた設定や脚本を凍結するのでもなく、核を共有しながら反復を許す「可変性のある基準資料」が必要になる。[S01, S04, S07]

歴史題材では、史実の再現を「正確／不正確」の二値で終わらせない。**何を史料で確認できたか、何が解釈か、何をゲーム上の創作・圧縮としたか**を区別し、その判断が人物像、空間、ルール、プレイヤーの行為にどう反映されたかを記録する。歴史的ゲームは物語だけでなく、ルール／シミュレーションも過去についての主張を生む。[S09–S12]

## 2. 調査範囲・方法・証拠の読み方

これは、公開されている査読論文、大学リポジトリの学位論文、欧州業界団体資料、およびスタジオ／開発者の一次発信を対象にした**焦点化された文献・資料レビュー**である。中心的な根拠は、ゲーム開発実務の実証研究、開発者インタビュー、スタジオでの参与観察、ナラティブ職務の求人分析、歴史ゲームのケース研究である。参照文献ごとの識別子、著者・年、方法、地域、利用上の限界、URL／DOIはJSONLに収録した。

本レポートでの「現代ヨーロッパ」は、単に欧州企業の広報事例を集めることではなく、**北欧を含む欧州研究・スタジオ事例と、グローバル業界の実証研究を区別しつつ、欧州の制度・地域的多様性を踏まえて読む**という意味で用いる。欧州産業統計は企業数や雇用を示すが、ナラティブ制作工程を示す統計ではない。[S14] また、公開研究はプレイヤー経験の分析に比べ、制作現場の観察がまだ少ない。単一スタジオ事例や求人票から業界全体の標準を導くことはできない。[S01, S05, S06]

**証拠レベルの扱い**

- **A：** 査読論文／査読会議論文（実証・理論）。制作実態や概念モデルの根拠。ただしサンプル・地域・作品範囲に依存する。
- **B：** 大学の学位論文・研究機関資料。詳細な一次分析を含みうるが、査読論文と同列ではない。
- **C：** 開発者・スタジオの一次発信や求人票。実際の役割・公開された工程を把握するのに有用だが、自己記述／採用広報であり、完全な制作記録ではない。
- **D：** 業界メディアの取材・解説。事例の補足に使用し、一般化には使わない。

本カタログは「網羅的収集」を目標に、主要テーマを横断する資料を集めた**再現可能な基礎カタログ**であり、全ての欧州スタジオ・全言語圏・非公開資料を完全に網羅したものではない。日本語での整理は、原文の主張を越えて一般化しないように行った。

## 3. 研究から見た制作プロセスの特徴

### 3.1 イテレーションは「追加」だけでなく、削除・転換でもある

開発者インタビュー研究では、反復は細部の追加・磨き込みだけでなく、簡素化、要素の削除、あるいは企画の核自体を変えることを含む。Kultimaの研究は、ゲーム開発者28名のインタビューをもとに、反復が自然な作業である一方、コストや納期の制約と結びつくことを示す。[S02] したがって、反復を「毎スプリントに機能を足すこと」と同義にしてはならない。意思決定には「続ける」「変える」「削る」「保留する」の選択肢が必要である。

11名のゲームデザイン実務者へのインタビューを基にした研究は、デザイナーが一貫性を保つ固定要素と、変更に対応する柔軟性を両立させることを「永続性と変化のバランス」として説明する。[S04] 実務では、これを次のように具体化できる。

- **固定する候補：** プレイヤーに約束する中心体験、テーマ、世界の基本ルール、対象プレイヤー、品質基準、制約。
- **探索可能にする候補：** 台詞、場面順、クエストの導線、人物の見せ方、環境描写、分岐の粒度、歴史情報の提示方法。
- **ゲートで再交渉する候補：** シナリオ量、分岐数、ボイス量、ローカライズ量、固有アニメーション、人物・ロケーション数。

### 3.2 Agile／PDCAはラベルよりも実際の意思決定を設計する

実証レビューは、制作上の不確実性に対応するため、創造的自律、水平的なコミュニケーション、チーム判断などが用いられる一方、スタジオ間・作品間の差が大きく、「Agile」という言葉が統一された方法を指さない場合があると指摘する。[S01] 公開ポストモーテム20件の分析でも、反復型、ウォーターフォール型、ハイブリッド型が並存している。[S03] このため、プロセス名を採用しただけでは改善にならない。各イテレーションに、**仮説、責任者、実物の成果物、評価基準、意思決定、学習の記録**を持たせる必要がある。

### 3.3 ドキュメントは巨大な「完成GDD」ではなく、変更を伝える仕組み

小規模独立系スタジオ4社を対象とした研究では、網羅的なGDDは一般的ではなくなっても、文書の機能（方向性の共有、作業の調整、判断の履歴など）はWikiや複数の媒介物へ移っている。[S07] 実務に必要なのは百科事典的な一冊より、**更新者・承認者・版・依存先が明確な「生きた設計資料」**である。ナラティブ変更がレベル、音声収録、字幕、演出、フラグ、QAに与える影響を追える変更台帳が不可欠となる。

## 4. 推奨する統合パイプライン

下表は、研究知見をゲーム制作に使える形へ統合した提案であり、既存スタジオの全社共通規格ではない。小規模インディーは役割を兼任し、AAA／複数拠点では専門職・承認点・ツール連携を細分化する。

| フェーズ | 目的・ナラティブ作業 | 主な成果物 | 検証・ゲート（Check） |
|---|---|---|---|
| 0. 企画・探索 | 対象プレイヤー、ジャンル、中心体験、差別化要素を定義。物語がゲームプレイに何を加えるかを仮説化 | 1ページのビジョン、ナラティブ・ピラー、プレイヤー体験仮説、リスク一覧 | 試作すべき最大リスクは何か。物語は遊びの行為にどう関係するか |
| 1. コンセプト／プリプロ | 世界の前提、テーマ、人物の欲求・葛藤、物語構造、レベル進行、歴史調査方針を共同設計 | ハイレベル・ビート表、世界設定の骨格、キャラクター関係図、トーンガイド、史料台帳、プロトタイプ計画 | 重要な未確定事項を明示。物語が必要とする量・機能・資源がチーム能力と整合するか |
| 2. プロトタイプ／縦切り | 最小の代表区間で「遊びながら物語が伝わるか」を確認。プレースホルダーでも、実際の導線・会話・状態変化を通す | プレイ可能なシーン／クエスト、会話・クエストの仮実装、縦切り、台詞・アセット工数の見積もり | プレイヤー理解、選択の意味、ペース、技術可否、作業時間。文章のみでなくプレイ結果を観察 |
| 3. 本制作 | エリア／クエスト／人物／イベント単位に分解し、並行制作と統合を反復 | 変更可能なナラティブ仕様、台詞・字幕データ、クエストグラフ、世界設定データ、実装済みコンテンツ | 日次連携・定期プレイテスト・レビュー。依存関係、未決事項、手戻り、スコープを可視化 |
| 4. アルファ／ベータ／仕上げ | 全体の因果・動線・トーン・キャラクターアークを通しで確認。文章品質、ローカライズ、音声・字幕・アクセシビリティを仕上げる | ナラティブQA計画、分岐／状態テスト、用語集、ローカライズキット、修正一覧 | 進行不能・誤フラグだけでなく、理解度、矛盾、誤解、表象、歴史表示、声の一貫性を確認 |
| 5. 発売後／ライブ | 実際のプレイ、レビュー、問い合わせ、分析値から課題を優先づけ。追加コンテンツや修正へ反映 | パッチ・エピソード計画、既知問題、変更ログ、学習記録 | 改善が想定体験を損なっていないか。定量データを単独で「物語の良し悪し」と扱わない |

**パイプライン上の重要な接点**は、ナラティブが完成してから他部門へ渡す一方向の工程ではなく、①物語／ゲームデザイン、②ナラティブ／レベルデザイン、③脚本／実装ツール、④歴史調査／アート・環境、⑤開発／QA・ローカライズを往復可能にすることだ。レベルデザイン現場の研究では、物語の遅延がレベルの再設計・破棄につながり、複数職種の連携と明確な所有権・計画が重要とされた。[S05]

### 4.1 実務的なPDCA（提案）

| PDCA | 物語・世界構築で行うこと | 証跡 |
|---|---|---|
| **Plan** | 「プレイヤーがこの場面で何を理解／感じ／選ぶか」を仮説化。サンプル、成功条件、スコープ、担当・依存先、危険要因を定める | 仮説カード、受入条件、見積もり、依存関係、変更前の基準 |
| **Do** | 最小コストで紙／グレーボックス／ゲーム内実装を作る。文書だけで完結させず、操作可能な状態にする | ビルド、台詞表、実装チケット、史料根拠、テスト記録 |
| **Check** | プレイ観察、理解確認、選択ログ、QA、専門家レビュー、史実・表象レビューを行う。意図と実際のプレイを比較 | 観察メモ、理解度質問、欠陥・矛盾リスト、専門家コメント、テレメトリ |
| **Act** | 修正・採用・撤回・スコープ縮小・追加検証を選ぶ。変更影響を追い、世界設定やナラティブ資料、バックログを更新 | 決定ログ、改訂版、影響対象、再テスト条件、教訓 |

**入れ子にする周期：** 個々の台詞／イベント、クエスト／レベル、エピソード、マイルストーン、製品全体の各レベルに、小さな学習ループを置く。頻度は固定値を押しつけず、変更コストで調整する。たとえば台詞・フラグは日々の統合確認、クエストはスプリントごとのプレイ確認、物語の理解や人物の好感度は縦切り・アルファなど十分な文脈がある段階で調査する。

### 4.2 役割と責任の最小設計

役割名の実態はスタジオにより変わる。求人分析では、ゲームライター、ナラティブデザイナー等の責務が重なりながらも、執筆と台詞編集、実装・追跡・レビュー、ステークホルダー間の調整などに傾向が分かれる。[S06] Ubisoftのナラティブデザイン解説も、ライター／デザイナーの境界が重なり、ナラティブデザインがゲームシステムと脚本を接続する職務だと説明する。[S15] 一例として以下の責任を明示する。

- **Narrative lead/director：** 全体の物語体験、トーン、品質基準、優先順位、最終判断。
- **Writer：** あらすじ、人物、台詞、テキスト、改稿。
- **Narrative designer／quest designer：** 物語をプレイヤー行為・システム・状態・導線へ変換し、実装・追跡・テストする。
- **World designer／lore keeper：** 設定の一貫性、用語、年表、確定情報と未確定情報の管理。
- **Game／level designer、art、audio、engineering、QA、localization：** 物語を空間・ルール・表現・実装・検証・言語へ実現する共同オーナー。
- **Producer：** スコープ、能力、依存関係、マイルストーン、意思決定の場を整える。

各作業項目に「提案者」「実装責任者」「承認者」「影響を受ける部門」を設定する。小チームでは同一人物が複数役割を兼任してもよいが、**誰が最終決定し、誰へ変更を通知するか**は曖昧にしない。

## 5. 領域別の構築・評価

### 5.1 ストーリー

1. 物語をあらすじでなく**体験目標**として表現する（例：プレイヤーが情報不足のまま誰を信頼するか選ぶ）。
2. 主要な物語目標とゲーム上の目標・フィードバック・プレイヤー解釈を結びつける。GFI（Goals–Feedback–Interpretation）は、物語意図がシステムとフィードバックを介してどう解釈されるかを分析・設計する枠組みを示す。[S08]
3. ハイレベル構造とプレイ可能な区間を併走させる。全脚本の固定を待たず、機能する場面から因果・ペースを検証する。
4. 分岐は「分岐数」ではなく、状態差・関係変化・プレイヤーが認識できる帰結・制作／QA／翻訳コストで評価する。
5. プレイヤーテストでは「良かったか」だけでなく、目的・状況・人物の意図をどう理解したか、選択が意味を持つと感じたかを聞く。

### 5.2 キャラクター

- 各人物に、**欲求、恐れ、価値観、矛盾、変化条件、プレイヤーとの関係、物語上の機能、システム上の役割**を与える。
- キャラクターアークをクエスト進行・プレイヤー選択・状態フラグと同期させる。カットシーン台詞に依存しすぎず、反応・行動・環境情報でも人物を示す。
- キャラクターの初登場から後日談までを状態遷移・イベント表で管理する。人物の一貫性、プレイヤーが選んだ結果の反映、意図しない矛盾をチェックする。
- 倫理・文化的表象の確認は発売前の最終承認だけでなく、キャラクター企画・コンセプト段階から複数の視点を参加させる。歴史ゲームの事例では、実在人物や証言、記憶の倫理的負荷をどう翻案するかが設計問題になる。[S11]

### 5.3 世界観・設定

「ワールド・バイブル」を大部の百科事典にしない。制作の意思決定に必要な**運用可能な設定体系**にする。

- **世界の約束：** ルール、技術／魔法、社会構造、地理、宗教、権力、日常生活。
- **時間：** 年表、前史、現在の状況、プレイヤーが変更できる出来事。
- **人物・組織：** 関係図、利害、呼称、視点。
- **表現：** トーン、視覚・音響の手がかり、用語と発音、地域差。
- **確度・状態：** canon確定／暫定仮説／創作／未決、根拠、責任者、最終更新。
- **制作影響：** どのレベル、台詞、アセット、システム、ローカライズ・QA項目が依存するか。

世界設定は陳列される情報の量より、プレイヤーの探索・行為・理解に一貫して返答するかで評価する。ゲーム開発は相互依存する専門職の作業であり、制作途中の変更を共有可能にする設計資料が必要である。[S01, S05, S07]

### 5.4 歴史・歴史的世界

歴史構築を行う作品では、次の**史料から実装までのトレーサビリティ**を推奨する。

1. **調査質問を切る：** 地域・時代だけでなく、建築、衣服、食、語彙、制度、人物、日常、地形など、チームが解決すべき具体的な問いにする。
2. **史料台帳：** 書誌、史料種、出典URL、時代・地域、利用範囲、確信度、反対説、最終確認日を記録する。
3. **確度ラベル：** 「史料で確認」「研究上の解釈／議論中」「ゲーム上の圧縮・合成」「創作」を区別する。沈黙している史料を確定事実のように扱わない。
4. **ゲームへの翻訳：** 史実を背景画にとどめず、地図、制度、資源、ルール、人物の選択、アクセス可能な知識に落とし込む。ルールも過去についての解釈を語る。[S09]
5. **継続的な専門家連携：** リサーチャー／歴史家をコンセプトから制作まで参加させ、台詞・クエスト・環境・アートの問いに随時応答できるようにする。Ubisoftの公開事例は社内歴史家と外部研究者の連携や、創作と歴史的根拠の「往復」を報じているが、これは大規模一社の例で、標準解ではない。[S16, S17]
6. **歴史検証とプレイ検証を別々にせず統合：** 史実に忠実でもゲームとして理解不能・不快・不公平な場合、何を優先したかを記録する。歴史性と遊びの緊張を開発者側の資源・時期が左右することが、フィンランドの小規模歴史ゲームのケース研究で示されている。[S09]
7. **複数視点と受け手：** 正確性は重要だが、プレイヤーは歴史的真正性やプレイを通じた過去の理解も評価する。過去を単線的に描くのではなく、解釈の余地・視点差・不確実性を扱う。[S11, S12]

## 6. 評価指標と「やってはいけない」運用

### 6.1 指標はゲーム種別と仮説に合わせる

**フロー／品質指標例：** 物語イベント完了率、進行停止率、必要情報の取得率、選択肢の理解度、ナラティブ上の因果の想起、同じ人物・出来事の矛盾数、台詞・字幕・音声の欠落、分岐別のテスト網羅率、1クエストあたりの統合手戻り、変更が関連チームへ伝わるまでの時間、史料根拠が記録された主張の割合。

これらを単純なスコア競争にしない。定量値は「どこに問題があるか」を特定する信号、プレイ観察・インタビューは「なぜそうなったか」を解釈する材料として組み合わせる。クリック／選択率やプレイ時間を、そのまま感情移入や物語品質の代理指標にしない。

### 6.2 典型的な失敗パターン

- **全脚本を先に凍結する：** プレイ結果やレベル都合を受け入れられず、大規模手戻りになる。
- **ナラティブを後工程にする：** 空間・アート・音響の文脈が遅れ、制作停止や作り直しにつながる。[S05]
- **長い文書だけを「共有」とみなす：** 更新責任・版管理・実装との紐づけがなければ、資料は現場を助けない。[S07]
- **反復を機能追加と取り違える：** 不要な要素の削除やスコープ調整ができず、feature creepを招く。[S02, S03]
- **「Agile導入」で問題が解決すると想定する：** 役割・判断権・評価サイクル・キャパシティが不明なら、儀式だけ増える。[S01, S03]
- **専門家レビューを最後に一度だけ行う：** 歴史・文化的な誤りの修正が高コストになる。専門家コメントの採否、ゲーム上の変更理由を残す。
- **スプリント速度を品質とみなす：** 反復の機会は増やせても、納期やリソース超過を無視すれば健全な制作にはならない。柔軟性と持続可能なキャパシティを両方管理する。[S01, S13]

## 7. 作品／地域事例から得られる示唆

### Ubisoft『Assassin’s Creed』シリーズ（フランス発・国際制作網）
社内歴史家、外部専門家、研究資料を使って、設定／歴史をコンセプトや脚本、環境制作に接続したとする公表事例がある。[S16–S17] 2024年の開発者取材では、脚本を書いた後にも歴史的検証を行い、誤認があれば動物・語彙などを修正するワークフローが説明されている。[S17] 学びは「膨大な調査」だけではなく、問いが生じる現場へ専門家が参加すること。ただし、公開記事・取材に基づく企業自己記述を第三者評価・全工程の監査記録と混同しない。

### Paradox『Crusader Kings III』（スウェーデン）
公式求人は、歴史研究を動的システム、ナラティブイベント、スクリプト実装、バランス調整へつなぎ、デザイナーが企画・実装・評価・修正に関与する職務像を示す。[S20] 歴史的事実を固定シナリオに再現するだけでなく、歴史的にもっともらしい選択肢をプレイヤーに与え、そこから異なる物語を生む設計として扱える。ただし求人は一職種の採用情報であって、プロジェクト全体の完全な制作フローではない。

### Charles Games／『Czechoslovakia 38–89: Assassination』（チェコ）
開発当事者による査読ケース研究は、証言・実在人物・争点のある歴史を、複数視点、真正性、構成主義、包摂性、文脈化の原則で扱い、歴史家・教育者・デザイナー間で会話をゲーム構造へ形式化する困難を具体化する。[S11] 歴史研究を脚本に移すだけでなく、誰の視点が含まれ、選択が何を意味し、どの文脈が必要かを設計対象にする例。

### フィンランドの小規模歴史ゲーム事例
『Steps of Struve』の研究は、ゲーム機能、歴史内容、技術、個々のメンバーの多役割性が相互作用すること、歴史研究に使える時間と資源の配分が設計判断を左右することを示す。[S09] 大規模スタジオの専任歴史部門を全チームの前提にせず、調査を小さな具体的問いへ分割して担当・レビューを割り当てる必要がある。

### 地域差に関する留保
北欧の制作文化・労働条件に関する研究は地域文脈を重視し、単一の「ヨーロッパ型」を想定することへの注意を促す。[S13] EGDFの産業報告も国ごとに調査方式が異なる統計の集成であり、欧州を単一組織として扱えない。[S14]

## 8. 導入用チェックリスト

**企画～プリプロ**
- [ ] プレイヤーへ約束する中心体験を一文にできる。
- [ ] 物語がゲーム上の行為・選択・空間にどう関係するか明文化した。
- [ ] 不確実な仮説、検証方法、判断期限を記録した。
- [ ] 歴史題材は史料調査の質問・担当・レビュー予算を設定した。
- [ ] 物語の核、変更可能箇所、凍結のタイミングを分けた。

**制作**
- [ ] 各クエスト／イベントに目的、プレイヤー情報、状態条件、完了条件がある。
- [ ] ナラティブとレベル／アート／実装／音響／QAに共通の担当・変更通知ルートがある。
- [ ] 台詞・設定・用語・史料根拠をバージョン管理している。
- [ ] プレイテストは開発者以外の視点も含み、観察記録を残す。
- [ ] 変更判断に「追加」だけでなく「削除・簡素化・延期」を含める。

**発売前後**
- [ ] 分岐・フラグ・ローカライズ・音声・字幕を統合状態で検証した。
- [ ] 史料上の事実／解釈／創作の区別が、チーム内および必要な場合はプレイヤー向けにも明瞭である。
- [ ] リリース後のデータを、ユーザー理解や質的調査と合わせて解釈する。
- [ ] 開発の学び、未解決事項、版、意思決定理由を次の企画へ引き継ぐ。

## 10. 結語

ヨーロッパのゲーム制作を一枚岩の「正解工程」に還元することはできない。実証研究が支持するのは、**核となる体験を保ちながら、プレイ可能な成果物で仮説を繰り返し検証し、学習を文書・ツール・スコープ判断へ戻す、協働的で適応的な制作**である。物語・人物・世界・歴史は別々のコンテンツ部門の成果物ではなく、ゲームのルール、空間、行為、演出、制作制約とともに作るプロダクト要素である。よって適切なPDCAは、物語を「完成させてから実装する」管理サイクルではなく、**意図とプレイヤーが実際に経験したものの差を発見し、チーム全体で次の判断をする学習サイクル**である。
