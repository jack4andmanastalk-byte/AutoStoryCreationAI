# 創作活動（世界観・キャラクター・ストーリー・歴史）におけるAIパイプライン・PDCAサイクル・プロダクト開発イテレーション実践カタログ＆アーキテクチャレポート

---

## 1. エグゼクティブサマリー

### 1.1 創作AIのパラダイムシフト：一発生成から「システム・パイプライン工学」へ
かつてのLLMを活用した創作活動は、「プロンプトに概要を入力し、長文を一括生成する（One-shot / Zero-shot Generation）」というアプローチが主流でした。しかしこの手法では、以下のような致命的な課題が発生します。

1. **コンテキスト忘却と矛盾（Hallucination / Narrative Inconsistency）**: 物語の後半で初期に死亡した登場人物が再登場したり、設定した魔法やテクノロジーの規則が勝手に改変される。
2. **キャラクターの口調・性格崩壊（Out of Character: OOC）**: 会話が進むにつれて誰が喋っても同じような優等生的トーンになり、本来のパーソナリティやトラウマ、エゴが消失する。
3. **プロットの停滞・脱線（Plot Drift / Lack of Dramatic Arc）**: 目標に向かって起承転結を描くことができず、同じような展開がループするか、唐突かつ不条理な結末を迎える。
4. **評価・改善サイクルの欠如**: 出来上がった原稿の何が優れていて何が破綻しているのかを客観的に測定・修正するループが存在しない。

現在、GitHubやHuggingFaceをはじめとする最前線のオープンソースコミュニティや研究機関（Google DeepMind, ACL/EMNLP/ICLR等のトップカンファレンス）では、創作活動を**「ソフトウェアエンジニアリングと同様のパイプライン構築およびPDCAサイクル（反復的イテレーション）」**として捉えるアーキテクチャへの完全なシフトが起きています。

### 1.2 本レポートの構成と選定基準
本レポートでは、「ストーリー」「キャラクター」「世界観」「歴史」の4要素を破綻なく構築・運用するために必要な**パイプラインオーケストレーション、ナレッジグラフ管理、キャラクターペルソナ維持、および評価・テストハーネス（Evaluation Harness）**を包括的に調査しました。

実用性（Codebaseの完成度、再現性、ライセンス、現代のLLMスタックへの適合性）が高いと評価される**20件の主要GitHubリポジトリおよびHuggingFaceデータセット/モデル**を厳選し、詳細な技術解説とともにカタログ化しています。また、使用した情報源の全メタデータは、後続システムやスクリプトで即時活用可能な `creative_narrative_tools_metadata.jsonl` として保存されています。

## 2. 創作活動における「PDCAサイクル」とプロダクト開発イテレーション

ソフトウェア開発における「アジャイルイテレーション」や「CI/CD」の概念は、創作活動のパイプラインにそのままマッピングすることができます。

```
   ┌─────────────────────────────────────────────────────────────┐
   │                  Plan (構想・要件定義・設計)                │
   │  - World Bible (世界観/歴史/地理/法則)                      │
   │  - Character Spec (ペルソナ/動機/関係性/道徳軸)             │
   │  - Story Architecture (三幕構成/ビートシート/伏線ツリー)    │
   └──────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
   ┌─────────────────────────────────────────────────────────────┐
   │                  Do (実装・階層的生成・演技)                │
   │  - Hierarchical Generation (大綱 → 構成細綱 → シーン)       │
   │  - Graph-RAG / Lorebook (時間・認識フェンス付文脈注入)      │
   │  - Multi-Agent Co-Writing (監督・作家・役者エージェント)    │
   └──────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
   ┌─────────────────────────────────────────────────────────────┐
   │                  Check (テスト・評価ハーネス・監査)          │
   │  - Narrative Consistency Audit (矛盾・生存フラグ検知)       │
   │  - Character Fidelity Test (InCharacter / 心理面接)         │
   │  - Prose & Pacing Review (LitBench / 読者シミュレーター)   │
   └──────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
   ┌─────────────────────────────────────────────────────────────┐
   │                  Act (自己修復・リファイン・記憶同期)        │
   │  - Critique-Refine / Targeted Rewrite (局所・全体リライト)  │
   │  - Knowledge Graph Diff Update (正史台帳への差分反映)       │
   │  - Dynamic Re-planning (プロットの適応的再構成)             │
   └──────────────────────────────┴──────────────────────────────┘
                                  │
                                  └────────── 継続的ループ (次章・次シーンへ)
```

### 2.1 Plan（要件定義・世界観とキャラクターの設計）
- **World Bible（世界観・歴史の固定化）**:
  世界の普遍的な物理法則、魔法・科学の体系、地理、政治勢力、過去の歴史年表を「正史（Canon）」として定義。
- **Character Profile（キャラクター仕様定義）**:
  単なる外見や性格の羅列ではなく、行動原理（Goals / Motivations）、隠し事（Secrets）、他者との関係性（Relationships）、心理的特性（Big Five / MBTI / Moral Alignment）を構造化（JSON / YAML）。
- **Plot Architecture（プロット・伏線設計）**:
  全体のアーク（三幕構成、英雄の旅）から巻・章レベルのビートシート、伏線の発生と回収ポイントをグラフ構造として定義。

### 2.2 Do（生成・コンテキスト注入・マルチエージェント協調）
- **階層的展開（Hierarchical Generation）**:
  一度に本文を書くのではなく、「全体プロット → 章のビート → シーンのト書き → 対話・描写」の順で段階的に詳細化（Decomposition）。
- **スコープ制御型RAG（Spoiler-Aware GraphRAG / Tiered Lorebook）**:
  全設定をプロンプトに入れるとトークン超過と幻覚を招くため、「現在の時間軸」「そのキャラクターが知り得る情報」に制限（フェンシング）した設定のみを動的注入。
- **ロール分担型エージェント協調**:
  進行役（Scene Director）、執筆役（Narrator）、登場人物（Character Agents）、記録役（Chronicler）がオーケストレーション上で役割分担してシーンを紡ぐ。

### 2.3 Check（検証・テストハーネス・品質監査）
- **設定矛盾のユニットテスト（Consistency Bug Detection）**:
  生成されたシーンを「世界観バイブル」や「直前までの事実関係」と突合し、整合性違反（Contradiction）を引用付きで自動検出（例: `ConStory-Bench`）。
- **キャラクター性格忠実性テスト（Psychological Interviews）**:
  エージェントに心理テストやブラインドインタビューを実施し、設計したペルソナから逸脱していないかをテストハーネスで計測（例: `InCharacter`）。
- **文学性・ドラマ性の客観評価（Human-Aligned Evaluation Harness）**:
  人間の選好に合わせた評価モデルや読者シミュレーターにより、テンポ、語彙の豊かさ、クリシェ（紋切り型表現）の有無を多次元スコアリング（例: `LitBench`）。

### 2.4 Act（改善・修正・ナレッジ同期）
- **Critique-Refine ループ（批評に基づく局所修正）**:
  Checkフェーズの指摘に基づき、文法修正（Refine）、感情線の強調（Polish）、破綻個所のピンポイント書き直し（Targeted Rewrite）を実行。
- **Graph Diff Update（状態と記憶の同期）**:
  シーン内で生じた新たな事実（アイテムの取得、人間関係の変化、負傷、死亡）を検出し、ナレッジグラフへ差分（Diff）として書き戻す。
- **動的再計画（Dynamic Re-planning）**:
  予期せぬ展開やキャラクターの自律的選択によって当初のアウトラインと乖離が生じた場合、以降の章のアウトラインを自動再編成する。

### 3.1 【カテゴリ1】統合ストーリー生成パイプライン・マルチエージェントオーケストレーション

#### 1. SAGA (Semantic And Graph-enhanced Authoring)
- **URL**: `https://github.com/Lanerra/saga`
- **リポジトリ種別**: GitHub (OSS)
- **主要機能**:
  - **LangGraphによるオーケストレーション**: 長編小説の執筆工程をステートマシンとしてモデル化し、いつでもチェックポイントから中断・再開可能。
  - **Neo4j永続ナレッジグラフ**: キャラクター、場所、関係性、過去の出来事（エピソード）をグラフデータベースに保持し、設定の正史（カノン）を永続化。
  - **ローカルファースト設計**: 人間が読めるMarkdownアーティファクトとローカルファイルシステムに出力。
- **PDCA/イテレーションにおける役割**:
  シーン執筆時にグラフから関連知識を取得（Graph-RAG）し、執筆後に発生した新しい事実関係をNeo4jへフィードバック更新する「Plan → Do → Act」の永続ループを実現。
- **実用性評価**: **極めて高い**。LangGraphとNeo4jというエンタープライズ級のスタックを採用しており、長編商業作品のバックエンド基盤として極めて堅牢。

#### 2. Agents' Room (Tell Me A Story)
- **URL**: `https://github.com/google-deepmind/tell_me_a_story`
- **リポジトリ種別**: GitHub (Google DeepMind / ICLR 2025)
- **主要機能**:
  - **物語論（Narrative Theory）に基づくタスク分割**: 執筆プロセスを「計画エージェント群」と「執筆エージェント群」に分離。
  - **計画専門エージェント**: Conflict（葛藤）、Setting（舞台設定）、Character（登場人物）、Plot（筋書き）の4エージェントが協議。
  - **劇的展開エージェント**: Exposition（導入）、Rising Action（上昇）、Climax（頂点）、Falling Action（下降）、Resolution（結末）の各ステージを個別の執筆エージェントが担当。
  - **共有スクラッチパッド**: エージェント間で状態や決定事項を共有するホワイトボードアーキテクチャ。
- **PDCA/イテレーションにおける役割**:
  単一プロンプトによる一括生成を排し、計画段階でのレビューと執筆段階でのステージ別生成によって、起承転結の明確なストーリー構築を保証。
- **実用性評価**: **最高レベル**。Google DeepMindによる査読付き論文（ICLR 2025）の実装であり、マルチエージェント創作パイプラインの標準設計思想（リファレンス）として必読。

#### 3. DOC: Improving Long Story Coherence With Detailed Outline Control
- **URL**: `https://github.com/yangkevin2/doc-story-generation`
- **リポジトリ種別**: GitHub (Kevin Yang et al. / ACL 2023)
- **主要機能**:
  - **階層型詳細アウトライン生成**: 目標とするプロットを深さレベル（Level 1〜Level 3等）に応じて再帰的に詳細化。
  - **詳細コントローラー（Detailed Controller / FUDGE拡張）**: 文章生成時に、現在の詳細アウトラインから逸脱しないようトークン生成確率（ロジット）または候補文をリアルタイムで再順位付け（Reranking）。
  - **関連性・一貫性リランカー**: 過去の文脈および将来のアウトライン目標との整合性を判定。
- **PDCA/イテレーションにおける役割**:
  人間による執筆と同様の「プロットの階層的練り込み（Plan）」と「執筆中のリアルタイム脱線チェック＆軌道修正（Check/Act）」をアルゴリズムとして体系化。
- **実用性評価**: **高い**。LLMが数千〜数万語の生成で直面する「プロットの忘却と脱線」を数学的・体系的に防ぐ実績あるアプローチ。

#### 4. STORYFORGE
- **URL**: `https://github.com/HieuNTg/STORYFORGE`
- **リポジトリ種別**: GitHub (OSS)
- **主要機能**:
  - **2層パイプラインアーキテクチャ**: L1（大枠ストーリー生成）→ L2（ドラマシミュレーション）→ 任意のL3（五感・描写の洗練）。
  - **13の特化型エージェント**: ドラマ批評家（Drama Critic）、編集者（Editor）、ペーシング監視（Pacing）、対話専門（Dialogue）、読者シミュレーター（Reader Simulator）等。
  - **6次元LLM-as-a-Judge自動リビジョン**: 生成結果を多次元で採点し、基準に達しない場合は自動でリライトを実行。
  - **FastAPI + SSEストリーミング**: リアルタイムで生成進捗を可視化。
- **PDCA/イテレーションにおける役割**:
  下書きに対して批評家エージェントがフィードバックを返し、エディターが修正する「完全自動のPDCA推敲ループ」を内蔵。
- **実用性評価**: **極めて高い**。Webフレームワークとして完成しており、即座にAPIやWeb UIと統合可能。

#### 5. Vela: AI-powered IDE for Novel Writing
- **URL**: `https://github.com/jjunho/vela`
- **リポジトリ種別**: GitHub (OSS)
- **主要機能**:
  - **作家向けAI統合開発環境（IDE）**: 世界観・キャラクター設定の一元管理、三幕構成や英雄の旅に基づくアウトライン自動生成。
  - **三重後期管線（3-Tier Post-Processing Pipeline）**:
    1. **Rewrite（推敲）**: 段落単位または章全体のスマートリライト。
    2. **Refine（精修）**: 誤字脱字、文法、論理矛盾の自動検出と修正提案。
    3. **Review（自評）**: 読者・編集者の視点でリズム、キャラクターアーク、伏線回収度を評価。
- **PDCA/イテレーションにおける役割**:
  プロダクト開発のイテレーション（Draft → PR → Code Review → CI Test → Release）を小説執筆に置き換えた直感的なワークフロー。
- **実用性評価**: **最高レベル**。ローカルLLM＋BYOK（Bring Your Own Key）対応で、実クリエイターが今すぐ使えるUI/UXが完成している。

#### 6. Write AI Agent
- **URL**: `https://github.com/Leolai6-7/write_ai_agent`
- **リポジトリ種別**: GitHub (OSS)
- **主要機能**:
  - **2段階パイプライン（構想・執筆）**:
    - Stage 1: 世界観バイブル（Wiki形式）、キャラクター名簿、ボリューム別構成、伏線台帳の自動設計。
    - Stage 2: 巻・章ごとの執筆ループ。
  - **3系統コンテキスト検索（assemble_context.py）**: 構造（構成案）＋グラフ（関係性）＋セマンティック検索（RAG）を統合。
  - **NetworkXストーリーグラフ差分更新**: 章を書き終えるごとにエージェントがグラフ差分（Diff）を算出し、`update_graph.py` で正史を更新。
- **PDCA/イテレーションにおける役割**:
  Gitのコミット＆プッシュのように、執筆した章の成果（キャラクターの成長、死亡、新アイテム）をグラフへ差分反映し、次章へ引き継ぐイテレーション管理。
- **実用性評価**: **高い**。Pythonスクリプト群が簡潔にモジュール化されており、自社開発パイプラインの部品として流用しやすい。

### 3.2 【カテゴリ2】世界観（Worldbuilding）・歴史・ロア・ナレッジグラフ管理

#### 7. Loreum
- **URL**: `https://github.com/loreum-app/loreum`
- **リポジトリ種別**: GitHub (OSS)
- **主要機能**:
  - **エンティティ管理**: キャラクター、場所、組織、カスタム型スキーマ（裏設定や秘密情報を含む）。
  - **ビジュアルナレッジグラフ（React Flow）**: 世界のあらゆる要素のつながりを視覚的に編集。
  - **インタラクティブガントチャートタイムライン**: イベントや時代区分（架空のカレンダーシステムにも対応）をドラッグ＆ドロップで管理。
  - **MCP（Model Context Protocol）サーバー内蔵**: AIエージェント（Claude、Cursor等）から直接世界観データベースを読み書き可能。
- **PDCA/イテレーションにおける役割**:
  世界観構築の「シングル・ソース・オブ・トゥルース（正史）」を提供し、AIエージェントが執筆・検証時にリアルタイムで歴史やルールを問い合わせるインフラとなる。
- **実用性評価**: **最高レベル**。MCP対応により、既存のLLMエージェントエコシステムとシームレスに連携可能。

#### 8. Lorebook AI (by Bcpoole)
- **URL**: `https://github.com/Bcpoole/lorebook`
- **リポジトリ種別**: GitHub (OSS)
- **主要機能**:
  - **LangGraph世界観ワークフロー**: 世界設定とコンパニオンキャラクターの生成フローを有向グラフ（DAG）で定義。
  - **専門エージェント分割**: タイトル、プロット、歴史、キャラクター、ロケーション、オブジェクト、オープニングを各専門エージェントが分担生成。
  - **Svelte製アーティファクトギャラリー/エディタ**: 生成されたJSONスキーマを視覚的にプレビューし、個別に修正・再生成可能。
- **PDCA/イテレーションにおける役割**:
  世界観のパーツ（歴史、法則、地理）をモジュール化し、不整合が発生した部分のみを局所的に再生成（Refine）するパイプラインを提供。
- **実用性評価**: **高い**。LangGraphによる状態管理とモダンフロントエンドが組み合わされており、ツール開発の雛形として最適。

## 4. 実践的パイプライン構築アーキテクチャ例（設計パターン）

本調査で得られた知見を統合し、実プロダクト（長編小説生成、RPGシナリオエンジン、IP世界観管理）にそのまま適用できる**「自律型創作エージェント・エンジニアリング・スタック」**の設計例を示します。

### 4.1 システムアーキテクチャ構成図

```
[ 入力: 企画・テーマ・シード ]
               │
               ▼
┌────────────────────────────────────────────────────────┐
│ 1. 構想・世界観設計フェーズ (Plan)                     │
│    - World Architect: 世界観・歴史年表・物理法則生成   │
│    - Cast Designer: キャラクターカード(CCv3)生成       │
│    - Plot Outliner: 三幕構成/ビートシート階層化 (DOC型)│
│    - Storage: Neo4j (正史ナレッジグラフ) & Lorebook    │
└──────────────────────────────┬─────────────────────────┘
                               │
                               ▼
┌────────────────────────────────────────────────────────┐
│ 2. 執筆・シミュレーションループ (Do) (各章・各シーン)  │
│    - Context Assembler: タイムライン制限付きGraphRAG   │
│    - Director Agent: シーンの目標・障害・結末を指示    │
│    - Character Agents: 各自の知識・動機から台詞を発話  │
│    - Narrator Agent: 散文ドラフトの生成                │
└──────────────────────────────┬─────────────────────────┘
                               │
                               ▼
┌────────────────────────────────────────────────────────┐
│ 3. 評価・テストハーネス (Check)                        │
│    - ConStory-Checker: 設定・因果関係の矛盾を引用検出  │
│    - InCharacter Test: キャラクターの口調・性格維持確認│
│    - LitBench Grader: テンポ・語彙・クリシェの採点     │
│    - [合否判定ゲート]: スコア >= 閾値 ?                │
└───────────────────────┬───────────────┬────────────────┘
                        │ 合格          │ 不合格 (リライト指示)
                        │               ▼
                        │      ┌─────────────────────────┐
                        │      │ 4. 修正ループ (Act)     │
                        │      │ - Rewrite / Refine Agent│
                        │      │ - 指摘箇所を局所修正    │
                        │      └────────┬────────────────┘
                        │               │ 再検証
                        │◄──────────────┘
                        ▼
┌────────────────────────────────────────────────────────┐
│ 5. 正史同期・状態反映フェーズ                          │
│    - Chronicler Agent: シーン内の重要事実・変化を抽出  │
│    - Graph Diff Updater: Neo4jへ新エッジ/ノードをコミット│
│    - Memory Pruner: 思考バッファの整理と次章への引継ぎ │
└────────────────────────────────────────────────────────┘
```

### 4.2 実装におけるベストプラクティス
1. **設定の「シングル・ソース・オブ・トゥルース（SSOT）」をナレッジグラフにする**:
   テキストのMarkdownファイルだけに頼ると、登場人物の関係性変化（「AがBを裏切った」等）が埋もれやすくなります。Neo4jやNetworkXなどのグラフDBを用いて「誰が何を知っているか」「誰と誰がどのような関係か」をトリプル（主語-述語-目的語）で永続化することが成功の鍵です（SAGA, Write AI Agentの採用パターン）。
2. **タイムライン・フェンシング（時間軸と認識の隔離）**:
   キャラクターが未来の展開を知っていたり、まだ会っていない人物の詳細を知っているという事故を防ぐため、コンテキスト取得時に「現在の章・時間」および「そのキャラクターの視点」でフィルターをかける機構（StoryWeaveのSpoiler-Aware機能）を組み込みます。
3. **LLM-as-a-Judgeに「引用（Quotes）」を義務付ける**:
   評価ハーネス（Check）において、単に「矛盾がある：70点」と出力させるのではなく、ConStory-Benchのように「第3章の『彼の手は無傷だった』という記述は、第1章の『右腕を失った』という記述と矛盾する」と引用付きで出力させることで、後続の修正エージェント（Act）が正確にピンポイント修正を行えるようになります。
4. **三重ポストプロセス（Rewrite → Refine → Review）**:
   本文を一度に完璧にしようとせず、VelaやSTORYFORGEが実践しているように、「粗削りなドラフト生成 → 誤字・文法・論理バグ修正 → 読者視点でのリファイン・味付け」と段階を分けることで、全体の一貫性と文章の美しさを両立させます。

## 5. 保存されたメタデータ（JSONL）の活用方法

本調査で収集した全20件のツール・リポジトリ・データセットの詳細メタデータは、同ディレクトリ内の以下のファイルに保存されています。

- **ファイル名**: `creative_narrative_tools_metadata.jsonl`
- **形式**: JSON Lines（1行1JSONオブジェクト、UTF-8）
- **格納フィールド**:
  - `id`: 一意の識別子
  - `name`: リポジトリ/プロジェクト名
  - `platform`: ホスト先（GitHub または HuggingFace）
  - `url`: 公式リポジトリ / 論文 / データセットのURL
  - `category`: 機能カテゴリ（パイプライン、世界観、キャラ、評価ハーネス等）
  - `pipeline_stage`: PDCAサイクルにおける対応ステージ
  - `tech_stack`: 使用言語、フレームワーク、アーキテクチャ
  - `description`: 機能概要
  - `pdca_role`: PDCAおよびイテレーションにおける具体的な役割
  - `practicality`: 実用性評価・推奨ユースケース

### Pythonでの読み込みサンプルコード
```python
import json

with open("creative_narrative_tools_metadata.jsonl", "r", encoding="utf-8") as f:
    for line in f:
        item = json.loads(line.strip())
        print(f"[{item['category']}] {item['name']} ({item['platform']})")
        print(f"URL: {item['url']}")
        print(f"PDCA Role: {item['pdca_role']}\n")
```

## 6. まとめと今後の展望

創作活動におけるAIの活用は、「プロンプト職人による単発の生成」から、**「ナレッジグラフ、ステートマシン、自動テストハーネスを組み合わせたプロダクト開発パイプライン」**へと完全に進化を遂げました。

特に注目すべきは、以下の3点です：
1. **LangGraphやMCP（Model Context Protocol）による標準化**:
   独自スクリプトの組み合わせから、ステートマシンやプロトコルを用いたモジュール性の高い協調システムへの移行。
2. **客観的評価ハーネス（InCharacter, ConStory-Bench, LitBench）の台頭**:
   主観的になりがちだった創作品質を、心理テスト、矛盾引用検出、人手選好アライメントによって定量テスト可能にしたこと。
   これにより、CI/CDのように「テストが通らなければリライトする」というエンジニアリング的PDCAが確立。
3. **ゲーム開発・トランスメディア展開への拡張**:
   世界観やキャラクターを一度グラフ構造・ロアブック化しておけば、小説執筆だけでなく、対話型ゲームのNPC、アニメ脚本、多言語翻訳へと低コストで横展開可能になったこと。

クリエイターやプロダクト開発者は、本カタログに掲載されたオープンソースのリポジトリやデータセットを活用することで、破綻のない壮大な物語世界を迅速かつ反復的（Iterative）に構築することが可能です。
