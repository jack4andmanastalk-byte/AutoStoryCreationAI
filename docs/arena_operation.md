- きっかけ: バッチ B の手順が「利用者がローカルで `.venv/bin/python …` を実行する」前提に
  読める、という指摘。
- 結論を先に: **指摘は正しい。ただしローカル前提なのは手順書（runbook）の宛先と
  対話シェル前提だけで、コード自体はローカル前提ではない。** 本リポジトリの既定運用は
  元々「Arena.ai だけを生成経路とする」（[`evaluation_scope.md`](evaluation_scope.md)）で、
  Arena Agent Mode のセッション内で実行と生成を完結させた前例もある。バッチ A/B の
  runbook が、人間が端末で実行する手順として書かれたことが後退だった。本書で分析と
  検証を記録し、運用モデルを再設計する。バッチ B の runbook は再設計に合わせて書き換えた。

## 1. 分析: 何がどこで動く前提になっていたか

| 層 | 現行の前提（文書上の宛先） | 実態 | 判定 |
| --- | --- | --- | --- |
| 決定論コード（`run_pipeline.py`、各 checker、`measure_*.py`、テスト） | ローカル端末で人間が実行 | 標準ライブラリ＋PyYAML のみ。Arena sandbox でも GitHub Actions（`.github/workflows/research-check.yml` が全テスト＋デモ検査を実行）でも動く | **ローカル前提ではない** |
| 生成（LLM 応答） | 人間が relay ファイルを別チャットへ運ぶ | API 鍵を持たない設計（`chat_operator.py`）。`docs/project.md` の運用モードは「モデルを Arena.ai のチャットに置き、生成の開始だけ人間が行う」。`experiments/2026-10-arena-l1-t01` では Arena Agent Mode の担い手自身が 45 リクエストすべてに応答して完走した前例がある | **本来の担い手は Arena セッション** |
| 状態・永続化 | ローカルの作業ディレクトリに残る | `runs/`・`build/` は揮発（`.gitignore`）。実験バンドル内の `relay/`・`sample-*/run`・`results.json` は版管理可能（`git check-ignore` で確認）。`chat_operator.py` の docstring 自体が「Arena/GitHub セッションを跨ぐ場合はバンドル内に置いて commit せよ」と指示している | **永続化層は GitHub が正** |
| 手順書（バッチ A/B の runbook） | 人間が対話シェルで関数・環境変数を維持しながら回す | Arena の実行環境はターン制で、シェル状態（関数・変数）は呼び出しを越えて持続しない前提と相性が悪い。利用者にローカル実行を求める形にもなっていた | **ここが誤り。再設計対象** |

つまり、計測コマンド `.venv/bin/python scripts/measure_realrun_b.py` 自体は移植可能で、
Arena 内でも GitHub Actions 内でも実行できる。「ローカルで実行する前提」に見えたのは、
手順書が**実行者を「端末の前にいる人間」と置いてしまった**ためである。

## 3. 再設計: Arena × GitHub 完結の運用モデル

### 役割

| 担い手 | 役割 |
| --- | --- |
| 利用者 | 実験の開始承認、結果の監査、**マージ判断**。ローカルでのコマンド実行はしない |
| Arena エージェント（Agent Mode） | sandbox 内での実行者。パイプライン駆動・生成（relay 応答）・計測・記録を担う。生成と計測の担い手が同一であることを明示し、応答の独立性は主張しない（従来どおり） |
| GitHub | 永続化層。セッションブランチへの commit / push で状態をセッション横断にし、PR の CI（`research-check`）で決定論部分を再検証する。マージは利用者の指示があるときだけ |

### 原則

1. **実行場所は Arena sandbox のチェックアウトを正とする。** コマンド自体は従来と同じ
   なのでローカルでも動くが、それは互換性であって前提ではない。手順書の宛先は
   エージェントとし、ターンごとに完結するコマンド列で書く（対話シェルの関数・
   環境変数の持続に依存しない）。
2. **状態はバンドルに置き、節目で GitHub に上げる。** relay の要求・応答、run 成果物、
   `results.json` は実験バンドル配下に置き、完走・終端失敗・計測の節目で
   セッションブランチへ commit / push する。sandbox が消えても GitHub から復元できる。
3. **生成の正直さは従来どおり。** エージェントが実際に生成した応答だけを逐語で
   取り込む。生成していない応答や、測っていない結果を書かない。provenance は
   記録された事実のみを使い、`unspecified` を新規生成とみなさない。
4. **非目標は維持する。** 常駐ワーカー・自動リトライ・完全自動運用は持たない
   （`docs/project.md` の運用モード）。生成の開始は利用者の指示による。
5. **計測は再現可能に。** 計測は決定論コードであり、コミット済み成果物から
   誰でも（CI でも）再実行できる。エージェントの報告は「実行した」という申告では
   なく、コミットされた成果物と CI で裏付ける。

  `command → chat_operator.py`、受け渡しも `relay_prompts.py` のまま）。

## 4. 残課題（今回はやらないもの）

- **計測の CI 照合**: `results.json` の再実行一致を CI で検証したいが、現行の
  `measure_*.py` は `run_dir` に実行環境依存のパス文字列を含むため、単純な diff では
  環境差で落ちる。パス表記を相対化してから別途入れる。
- **`relay_prompts.py ingest` の provenance**: 現状 `provenance.origin` を書かないため
  台帳では `unspecified` になる。応答の出所を明示的に記録する拡張は、登録済みバッチの
  実行条件を変えない範囲で別途検討する（後から書き換えることはしない）。
- ローカル実行の互換手順（README のクイックスタート等）は、データセット構築など
  Arena 外でも意味のある用途があるため残す。ただし実験手順の正は本書の運用モデルとする。

## 5. 保存先の事前確認と回答待ちチェックポイント（2026-10-28）

Arena の作業ディレクトリは実行場所であり、GitHub に push するまでは永続的な正本ではない。
`experiments/<id>/runs/<run-id>` と `relay/<run-id>` のようにリポジトリ内のパスを使い、
`python scripts/check_persistent_paths.py <run-dir> <relay-dir> <results-path>` で
Git ignore と既知のスナップショット除外名を確認する。特にどの階層でも `out/` と
`build/` は使わない。テストや仮想環境など再生成可能な一時ファイルは例外とする。

回答待ち・応答保存・完了の各節目で、入力、state、要求、応答、成果物を揃え、秘密情報・
個人情報・権利・サイズを点検した上で、対象ファイルだけを現在の作業ブランチに commit / push
する。push 失敗時は保存できたと報告しない。外部由来の大規模データは既存のデータセット
保存方式に従い、無条件に通常ブランチへ追加しない。再開は GitHub 上のチェックポイントを
復元して行い、保存先検査の成功だけで GitHub 保存を保証したとみなさない。
