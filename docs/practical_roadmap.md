## 1. 前提

本リポジトリの目的は、**AIによる自動創作活動そのもの**である。AIが題材や条件から
世界・歴史・人物・関係・物語構造・場面・文体と本文を作り、検査と修復を経て、
続き・改訂・分岐・編纂を続けられるようにすることを対象とする。

- 人間の役割は、題材と制約の指定、生成の開始、採用判断、読後のフィードバックである。
- 開始後の創作段はAIが進める。標準経路では、人間が本文を代筆することや、各段の成果物を手作業で運ぶことを前提にしない。
- 実行前提は Arena Agent Mode × GitHub とする（[`arena_operation.md`](arena_operation.md)）。
- 常駐ワーカーによる無人運用は当面の範囲外とし、必要性が実運用で出たときに扱う。
- データセット、創作技法の研究、13スキル、決定論的検査、過去の実験記録は、
  自動創作を支える基盤と履歴として保持する。

## 2. 改善の進め方

今後は、厳密な意味での「検証」より、実際に作品を作って直す循環を優先する。

1. AIに作品を最後まで作らせる。
2. 検査結果だけでなく、原稿そのものを読む。
3. 完走を妨げた点、手作業が多かった点、本文で気になった点を摩擦として記録する。
4. 一番困るものから、小さく直す。
5. 次の作品で同じ困りごとが減ったかを見る。

この方針では、1作品で見つかった実害でも直してよい。ただし、その観察を率・再発率・
因果効果として主張しない。プロンプト変更は版と変更理由を残し、決定論的な振る舞いは
回帰テストで守る。過去の事前登録と結果は書き換えない。

### 検査の位置づけ

- 検査は作品の良し悪しを証明するものではなく、形式崩れと明確な矛盾を早く見つける編集支援である。
- 標準経路を止めるのは、生成物の形が壊れるものと、明確に作品を壊すものに限る。
- 曖昧な所見は警告または観測として残し、書き手が不要に止まらないようにする。
- `clean` / `pass` は「検査した範囲で進める」という意味であり、面白さの保証ではない。

### 記録する実用指標

総合点は作らない。作業ごとに次を残せば足りる。

- 最後まで原稿が出たか
- pending、再試行、修復、手動介入の回数
- 未解決のまま残った blocker
- 読んで気になった箇所と、その分類
- 次の作品で同じ摩擦がどうなったか

## 3. 現在地

- S1全体（plan → 8設計 → draft → 監査）は実応答で通った記録がある（バッチB/B2）。
- `design-history` は、検査だけが知っていた契約をプロンプトへ明記した v1.1 になっている。
- 継続性監査は、死者の行為・発話と、参照としての言及を分けて記録できる。
- 創作projectの再開、continuation、改訂、分岐、入れ子、世界文脈、編纂、bundle は
  CLIから扱える（`docs/project.md`）。
- 一方で、入口は実験用 `run_pipeline.py`、二段階方式、創作projectへ分かれており、
  「標準で1本作る」導線はまだ一つに定まっていない。
- Arena relay の往復と状態確認には、まだ手作業の台帳管理が残っている。
- 本文の読み味は、個別の試走では見ているが、摩擦の分類として継続的には回っていない。

## 4. タスク整理

優先度は次の意味で使う。

- **P0**: 自動創作が最後まで進まない、または手作業が多くて標準経路にならない
- **P1**: 原稿の読みにくさや、大きな手戻りを生む
- **P2**: 長期・大規模運用で必要になる
- **後置**: 研究上の厳密さや、必要性が実測で出たときに扱う

| ID | 優先度 | タスク | 完了の目安 |
| --- | --- | --- | --- |
| U-01 | P0 | 標準自動創作フローを一つに決め、quickstart を作る | 題材と条件から3章の原稿まで、Arenaセッション内で迷わず進められ、最終成果物と状態が分かる |
| U-02 | P0 | Arena relay の一巡支援を整える | pending、次に処理する要求、取り込み後の次操作、完了・失敗が一つの作業単位で分かる。完了済み応答を再生成しない |
| U-03 | P0 | 実用dogfoodを回し、摩擦ログを作る | 単体作品、continuation、入れ子または世界の作例について、原稿と上位の困りごとが残る |
| U-04 | P0 | 失敗回復の標準路をそろえる | 設計1文書、1章、失敗stage、応答待ちごとに、次操作と選択的な再試行ができる |
| U-05 | P1 | 読後フィードバックでプロンプトと設計を直す | 長さ、説明過多、反復、会話、場面転換、伏線回収、文体など、実例に基づく変更が版つきで残る |
| U-06 | P1 | 検査の重大度と表示を編集支援として整える | blocker、警告、観測が分かれ、誤検出が標準経路を不要に止めない。人間向け要約で次に直す場所が分かる |
| U-07 | P1 | 編集・再生成の導線を標準化する | canon・設計の要約を確認し、特定の文書や章だけを直しても無関係な成果物が壊れない |
| U-08 | P1 | 原稿出力を読める形にそろえる | JSONを開かずに、結合原稿、作品情報、検査要約を読める |
| U-09 | P2 | 長期・世界スケールのdogfoodを行う | 複数作品、複数時間軸、長期中断をまたいで、実際に必要な運用機能が見える |
| U-10 | P2 | 規模対応は引き金が再現したときだけ行う | `doctor` や `compose` の実測が既定の目安を超えた場合に限り、index等を検討する |
| M-01 | 保守 | READMEと `protocol.md` の状態表を現在へ同期する | B/B2と監査変更が反映され、研究上の主張範囲は変わらない |

## 5. タスクの最小記録

新しい改善タスクは、事前登録ではなく次の最小記録で始める。

- きっかけになった作品またはrun
- 困りごとの分類（完走、本文、編集、運用）
- 行った変更
- 次の作品または回帰テストで見たこと
- 残した制限

プロンプトを変更する場合は、版、変更理由、動機になった実例を残す。過去の実験結果を
新しい規則で測り直した場合は、回帰確認と独立した検証を混ぜて書かない。

## 6. 着手順

1. **U-01** で標準入口を決める。
2. **U-02** でArena内の往復を減らす。
3. **U-03** で実際に作品を作り、摩擦の上位を決める。
4. その結果から **U-04〜U-08** を選ぶ。
5. **M-01** は小さい保守として並行してよい。

北極星は「正しく測れたか」ではなく、**AIが次の作品と次の章を、少ない手戻りで
作り続けられるか**である。

新しいArenaチャットで実作業を始める場合は、
[`practical_start_prompt.md`](practical_start_prompt.md) の開始プロンプトを使う。

## 7. 実施記録

### U-01 標準自動創作フローを一つに決め、quickstart を作る（2026-10-27）

- 決定: 標準入口は `scripts/story_project.py`（創作project）。provider の省略時は
  Arena relay（`<project>/relay`）。`run_pipeline.py` と `run_twostage.py` は
  凍結した実験条件の再実行経路として残す。
- 文書: [`standard_flow.md`](standard_flow.md)（決定）、[`quickstart.md`](quickstart.md)（手順）。
- 実装: `--provider arena`（および既定化）、`relay export|status|ingest`、
  応答待ち時の PROMPTS.md 自動更新、完成時の `Manuscript:` 表示、
  relay タグの 8 hex 化（4 hex が実際に衝突し、応答が別 request に付いた）。
- 回帰: `tests/test_standard_flow.py`、`tests/test_relay_prompts.py` の衝突テスト、
  `make quickstart-check`。
- 確認: 固定台本で premise → 3章 → render まで通した（実応答ではない）。
  記録と摩擦は [`experiments/2026-10-u01-standard-flow-t01/`](../experiments/2026-10-u01-standard-flow-t01/note.md)。
- 残り: 実応答での dogfood（U-03）。relay の一括書き出しと pending 表示の統一（U-02）。
  原稿の章見出しとマーカー表示（U-08）。L2/L3 は `frozen_not_measured` のまま。

### U-02 Arena relay の一巡支援を整える（2026-10-27）

- 追加: `relay submit`（取り込み + 再開）、`relay status` の1巡報告（`asc-relay-round-v1`）、
  終了コード `0` 完了 / `3` 応答待ち / `2` 失敗、`status` の `Relay:` 行。
- 変更: 待機中の next action を `relay export` に統一（`status` / `doctor` 共通）。
- 安全側: 完成済み・失敗済みの作品への `submit` は取り込まない（完成→`continue`/`revise`、
  失敗→`--retry-failed`）。回答済み要求は書き出さず、保存済み応答は書き換えない。
- 回帰: `tests/test_relay_round.py`、`make quickstart-check`。
- 確認: 固定台本で12ラウンド（各1コマンド）で完成。要求数12・応答数12のまま。
  記録は [`experiments/2026-10-u02-relay-round-t01/`](../experiments/2026-10-u02-relay-round-t01/note.md)。
- 残り: 往復回数そのもの（12）は減っていない。1応答で複数成果物を返す契約変更は、
  検査の粒度が変わるため実運用で必要性が出てから扱う。実応答の確認は U-03。

### U-03 実応答 dogfood と上位摩擦の解消（2026-10-27）

- 実施: 『宛名のない手紙』（3章・目安900字）を題材と条件だけ人間が与え、
  世界・歴史・人物・関係・物語構造・場面・文体・本文の14件を Arena セッション内の
  実応答で生成し、relay で逐語的に取り込んだ（台本ではない）。14ラウンドで complete、
  `doctor` findings 0。記録は [`experiments/2026-10-dogfood-01/`](../experiments/2026-10-dogfood-01/note.md)
  （摩擦ログ F-18〜F-26）。
- 解消した摩擦:
  - **F-18**（導線）: `Next request` の stage 二重表示（`draft: draft:ch02`）を修正。
  - **F-19**（導線）: `relay/index.json` は export 時点の控えで、待ちの正は `relay status` と明記。
  - **F-23**（本文/プロンプト）: 場面設計で修復1往復の原因になった `foreshadows.planted` の条件
    （「canon の布石 ID は書かない、新規がなければ `[]`」）を `prompts/design-scene.md`
    （v1.0 → **v1.1**）と schema に明記。人物の「口調サンプル30字以上」は既に依頼文にあったため変更せず。
  - **F-22**（本文/表示）: `draft.json` に記録されていた字数目安からの外れ（`warnings_ja`）を、
    完成後の `relay status` / `relay submit` に `Warnings:` として表示（失敗にはしない）。
  - **F-17 / U-08**（編集/読書）: `render --reader` を追加。既定の `render`（検査マーカー込みの正本）は
    1バイトも変えず、`--reader` のときだけ章見出し（`## 第1章`）を付け `{{…}}` マーカーを外す。
- 残り: 単体3章は実応答で完走したが、continuation（第4章追加）と入れ子/世界の実応答 dogfood、
  および設計1文書・1章単位の失敗回復（U-04）が次。L2/L3 は `frozen_not_measured` のまま。
