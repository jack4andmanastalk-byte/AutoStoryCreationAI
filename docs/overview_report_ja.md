# AutoStoryCreationAI の現在地 — 一般向け概要レポート

**確認日:** 2026年10月25日　**対象:** このリポジトリのコミット `052c8f2` 時点のコード・設定・同梱記録。外部サービスの現在の稼働状況までは確認していません。

## 最初に、ひと言でいうと

これは**「AIに物語を書かせるための手順と、設定・原稿を管理して機械的な食い違いを調べるための研究用道具箱」**です。誰でもボタン一つで良い小説が完成するアプリではありません。文章を書くAIは内蔵されておらず、外部のモデルや、人がチャットとの間で回答を受け渡す仕組みにつなぎます。

今あるのは、①創作技法の資料、②13種類の「スキル」（作業手順と検査器）、③生成工程、④検査用の例題・採点基準、⑤作品と実行履歴を保存する仕組みです。**検査に通ったことは、作品が面白いことの証明ではありません。** 現在の研究では機械的に確かめられる項目だけを扱い、AIや人間による作品品質の評定は停止しています。根拠: [README](../README.md)、[評価の運用範囲](evaluation_scope.md)、[創作プロジェクトの説明](project.md)。

## 1. 何がどこにある？――料理にたとえた見取り図

## 2. 物語はどう作られる？――二つの入口

### A. 決められたお題で試す「実験用の道」

[`run_pipeline.py`](../scripts/run_pipeline.py) は固定の10題から一つを選びます。例えば「灯台の鍵」というお題なら、概ね次の順番です。

```text
お題 → Plan（人物・場所・日付などの設定台帳を作る）
     → Design（企画・世界・歴史・人物・関係・筋・場面・文体の設計書を作る）
     → Draft（3章の本文を書く） → 設定台帳と本文を照合
                          ↘ 必要ならS2で改稿 → S3で文体を当て直す
```

ここでいう**設定台帳（canon）**は「この世界で確定した人物・事実・場所・時系列・伏線」のメモ帳です。本文中には日時や登場人物の状態を表す目印（例: `{{time: day=3}}`）を入れ、後から台帳と照合します。目印がないと調べられない項目もあります。設計書は8種類を形式検査し、問題があれば最大2回試しますが、**直らなくても `unresolved` と記録して先へ進みます**。設計書の合格が生成全体の合格を保証するわけではありません。根拠: [Plan](../src/asc/pipeline/plan.py)、[Design](../src/asc/pipeline/design.py)、[Draft](../src/asc/pipeline/draft.py)。

比較用に4つの構成があります。**S0**は設定台帳・設計書を渡さない比較用、**S1**は上のPlan→Design→Draft、**S2**はS1の監査で直すべき箇所が見つかった場合に改稿・再監査を加え、**S3**はさらに文体に合わせて章を書き直します。S2は指摘がなければ**改稿0回**です。「S0は単発」という呼び名でも、現行コードは3章を章ごとに依頼します。実験の条件と記録は[評価プロトコル](protocol.md)、[パイロットの記録](../experiments/2026-10-arena-l1-t01/note.md)を参照してください。

AIへの接続は、決まった回答を返す**台本（`scripted`、動作確認用）**、外部プログラムとの接続（`command`）、チャットから回答をファイルで受け渡す[`chat_operator.py`](../scripts/chat_operator.py)＋[`relay_prompts.py`](../scripts/relay_prompts.py)から選びます。API接続用の[`model_adapter.py`](../scripts/model_adapter.py)も実装されていますが、リポジトリ内に実APIを用いた生成の実験記録は見当たらず、現在の研究運用はArena.ai経由に限定されています。**台本デモを「AIが生成に成功した実験」とは数えません。**

### B. 好きな題材を保存して育てる「創作プロジェクトの道」

[`story_project.py`](../scripts/story_project.py) なら任意の題材で作品を作れます。ただし現在の自動生成は**S1（Plan→Design→Draft）まで**で、実験用のS2/S3や最終的な作品品質の監査・合格ゲートは自動では通しません。ここでの「完成」は**工程が最後まで終わった**という意味です。[プロジェクト仕様](project.md)、[入力の変換方法](../src/asc/project/adapter.py)。

- **保存・再開:** 作品の題名、章、応答待ち、工程ごとの進捗と旧版を保存する。`status`・`pending` で次の作業を確認し、回答を入れたら `resume`。失敗した工程のやり直しには明示的に `--retry-failed` が必要。
- **続き・別案:** `continue` で章を追加し、`revise` で指定した章・設計書だけを作り直し、`branch` で別案を独立させる。**この `revise` は部分的な再生成で、実験用S2の「監査→自動改稿」とは別**。
- **作品群・世界:** 子作品を作って `run-tree` で親から順に進める。複数の暦・地域・文化の資料を保存し、使う版だけを選んで子作品へ渡す。`compose` は作品集を、`world compile` は年代記・地誌等の一覧を組み立てる。未完成の子は `compose --partial` で「未収録」と明示できる。歴史や文化の**内容が正しいことまで機械が保証するわけではない**。
- **後から確かめる:** `doctor` は保存記録の欠落や古い参照を点検し、`context show`・`diff` で何の設定を渡したかを見る。プロジェクトの `bundle` は記録を外部保存・検証・復元できる。

別に、**実験用の完了した実行**には、記録済み応答を用いた[`replay`](replay.md)があります。これは**昔の応答を再生する検査**であり、AIが同じ文章を再び書ける証明ではありません。

始動もチャットへの受け渡しも**人が行います**。常駐して勝手に次の仕事を進める仕組み、失敗時の自動リトライ、Web画面はありません。生成した本文や応答は通常 `runs/` に置かれ、Gitには入りません。後から再生したければ、応答の実体ごと保存・`bundle` で退避する必要があります。根拠: [運用モード・保存先](project.md#運用モード人間が開始する)、[保存形式](project.md#保存形式)。

## 3. 「スキル」13種類で実際にすること

スキルは**物語の上手さを教える魔法ではなく、作業手順と、決めた形式・参照をチェックする約束**です。通常の短編で設計書として直接作るのは最初の8種類。残りは監査工程か、用途別の単独ツールです。

| 使う場所 | スキル | 普通の言葉でいうと |
| --- | --- | --- |
| 設計① | [企画核](../skills/premise-brief/SKILL.md) | 誰が、何を望み、何に阻まれるかを、短い企画書にする。 |
| 設計② | [世界の規則](../skills/world-rules/SKILL.md) | 世界の決まり、使う代償、例外の条件を書き出す。 |
| 設計③ | [歴史・年表](../skills/history-timeline/SKILL.md) | 出来事の順序、原因、今に残る痕跡を整理する。 |
| 設計④ | [人物の核](../skills/character-core/SKILL.md) | 人物の欲望・必要な変化・恐れと、選択の一貫性を設計する。 |
| 設計⑤ | [人物関係](../skills/relationship-web/SKILL.md) | 表向きの仲と本当の利害、誰が何を知っているかを整理する。 |
| 設計⑥ | [筋立て](../skills/plot-architecture/SKILL.md) | 幕・転換点・副筋・結末のつながりを記録する。 |
| 設計⑦ | [場面の情報](../skills/scene-information/SKILL.md) | 各場面で何を変え、読者に何を教え、伏線をいつ回収するかを決める。 |
| 設計⑧ | [語り・文体](../skills/voice-style/SKILL.md) | 誰の視点で語るか、使わない言い回しなどを決める。本文の視点検査は別コマンドでも行う。 |
| 本文の後（実験用）／単独 | [整合性台帳](../skills/continuity-ledger/SKILL.md) | 死者の再登場、未習得の情報、日付・移動日数、伏線などの食い違いを探す。 |
| S2／単独 | [改稿ループ](../skills/revision-loop/SKILL.md) | 見つかった問題を修正指示にし、修正前後を比べる。 |
| 個別利用 | [分岐構造](../skills/interactive-branch/SKILL.md) | 選択式の物語で、到達不能や行き止まりを調べる。通常の直線的な短編には入らない。 |
| 個別利用 | [翻案](../skills/adaptation/SKILL.md) | 別媒体に移す際、原作の役割や削除理由・権利の記録漏れを調べる。通常の短編には入らない。 |
| 別の評価コマンド | [評価ハーネス](../skills/evaluation-harness/SKILL.md) | 指標・欠陥と次に直す場所を報告する。現在使うのは下記のL1だけ。 |

設計書に「項目がある」と分かっても、その設定が魅力的か、文章で自然に表現できたかまでは分かりません。目印の無い状態変化や、台帳にない情報も調べきれません。「問題0件」は**見た範囲で0件**という意味です。根拠: [設計工程の対象と限界](../src/asc/pipeline/design.py)、[監査スキルの限界](../skills/continuity-ledger/SKILL.md)。

## 4. 「ハーネス」と評価の現在地

**ハーネス**は、ものさしが壊れていないか試す「試験台」です。[`harness/cases/`](../harness/README.md) に良い例・悪い例と期待結果、[`patterns.yaml`](../harness/patterns.yaml) に禁止表現、[`rubrics/`](../harness/rubrics/story-quality-v0.yaml) に評価基準があります。「わざと7件の食い違いを入れた5章」の例では、監査器が7件を指摘します。これは仕込んだ例で機械が動くことの確認で、未見の作品に対する正確さの証明ではありません。

| 層 | 何を調べる？ | 今の扱い |
| --- | --- | --- |
| **L1** | 必須語・禁止表現、台帳と本文の食い違い、調べられた範囲、文字数など | **現在の実験対象**。決めた規則に沿って機械的に数える。 |
| **L2** | 文章の一貫性、人物、独自性などを別のAIに根拠つきで判定させる | 道具と固定の模擬回答はあるが、**新規の実評価・較正は凍結中**。`make evaluate` の点数は模擬回答の再生。 |
| **L3** | 読者がどちらを選ぶか、誰が書いたと思うか | ラベル形式等は残るが、**新規の人間評定は凍結中**。 |

現行の研究条件は**Arena.aiでの生成×L1**。モデルの版を固定できないため、L1の数値も**探索的な参考値**です。ただし使うコマンドで集計項目は異なります。例えば[`run_experiment.py`](../scripts/run_experiment.py)の既定集計には禁止パターンの密度は含まれず、これは別の評価コマンドなどで計測します。全実行で全項目を調べたと考えないでください。

評価規約の5条件のうち、G3/G4（読者による比較・識別）は未測定、G5（同条件での再現）は主張していません。総合点や「人間と同等の小説が書ける」という結論は出せません。対照の青空文庫30作品は選定済みですが、**人間による品質評価が済んだという意味ではありません**。根拠: [運用範囲](evaluation_scope.md)、[評価規約](protocol.md)、[対照群の承認記録](../benchmarks/protocol-v1/controls.approved.json)。

## 5. データ・保存・日々の自動チェック

- **データ:** 収集の仕組みは[`setup_dataset.py`](../scripts/setup_dataset.py) と[`configs/dataset.yaml`](../configs/dataset.yaml)。同梱の[`manifest.json`](../data/datasets/manifest.json) には、過去の生成記録として青空文庫書誌17,840件、なろう書誌23,666件、なろう300作品の本文と5ジャンル追加73作品の本文を扱った記録があります。一方、**今のチェックアウトの `data/datasets/` にはmanifestしかなく、`data/raw/` はありません**。`samples/` に書誌の抜粋・373作品の一覧（本文ではない）・小さな本文サンプルがあります。全本文はこの作業フォルダに同梱されていません。取得には別途ダウンロード・容量・取得先の利用条件の確認が必要です。
- **実行履歴:** 実験の実行結果は `runs/`（Git管理外）、短い結果・注意書きは[`experiments/`](../experiments/README.md)。実際のArena実験記録もありますが、[t01のS0～S3パイロット](../experiments/2026-10-arena-l1-t01/note.md) は各1回でS2改稿0回、[t02・t03のS1記録](../experiments/2026-10-arena-fresh-s1-t02t03/note.md) も探索的な範囲です。固定10題すべてで品質を実証した記録ではありません。
- **自動チェック（CI）:** [research-check](../.github/workflows/research-check.yml) はコードのpushやPRで、研究カタログの一致・テスト・固定デモを確認します。[dataset-refresh](../.github/workflows/dataset-refresh.yml) は別の重いデータ更新用で、月次・手動等で起動する設定です。**どちらも日常的に新作小説を書き続ける仕組みではありません。**

### まず安全に見てみるなら

Pythonと必要なパッケージを入れた環境で、リポジトリのルートから次を実行できます。`make setup` のみ依存パッケージの取得が必要で、その後のデモ・検査には外部の生成AIは要りません。

```bash
make setup   # 動作環境を用意
make audit   # わざと仕込んだ7件の食い違いを検出
make story   # 固定のお題を、用意された回答で工程だけ試す
make ci      # カタログ・テスト・固定デモを一通り点検
```

**読み違えやすい点:** この時点で `make ci` は**549テスト成功、警告3件**でした。一方 `make story` / `make story-s2` / `make story-s3` は配線確認の短い台本なので、生成工程は動いても本文が規定の3,000～4,200字に届かず、内部の `status` は**`fail`**です。デモ用の `--report-only` によりコマンド自体は終了コード0になります。S2デモの改稿も0回です。**「コマンドが成功した」＝「小説の合格」ではありません。** 実AIへの接続、公開データの取得、GitHub上の最新CI結果は今回試していません。根拠: [Makefile](../Makefile)、[台本の実行コード](../scripts/run_pipeline.py)。

## 6. 利用前に気をつけたいこと

1. **権利:** コードのライセンスと、収集対象の作品の権利は別です。[権利・倫理メモ](legal_and_ethics.md) は「なろう作品の本文は作者の許可なく再配布できない」と書く一方、[データ公開のワークフロー](../.github/workflows/dataset-refresh.yml) は無料公開Web版の本文を配布対象として記述しています。**この配布と許諾の関係は、リポジトリの説明だけでは確認できません。** 本レポートは許諾の有無・適法性を判断していません。本文の取得・共有・学習や商用利用の前に、原典の条件と必要な許諾を別途確認してください。
2. **古い説明とのずれ:** [旧データ手順](data_setup.md) にはPDFを通常の成果物のように書いた箇所がありますが、現行の`make data`とデータ更新ワークフローは**テキスト中心・PDF削除**です。ただしプログラムには任意のPDF出力オプションが残ります。また[権利メモ](legal_and_ethics.md)の「R15は既定で除外」という記述に対し、現行[`configs/dataset.yaml`](../configs/dataset.yaml) は `include_r15: true` です。設定と今の実行コードを優先して確認してください。
3. **まだ無いもの:** 新作の面白さを保証する判定器、無人で走り続ける創作サービス、作品群の意味的な矛盾をすべて理解するAI、全スキルを自動選択する登録機構（skill registry）はありません。後者の拡張は[計画書](continuous_creation_roadmap.md#x-01-skill-registryは後置する)で将来の候補とされています。

### 短い用語集

- **スキル:** 作業手順＋入力の約束＋検査の方法。AIの内部能力や、品質の保証ではない。
- **ハーネス／fixture:** 検査器を試すための試験台／答えを用意済みの例題。
- **パイプライン:** お題から設定・設計・本文・検査へ進む工程のつなぎ方。
- **canon:** 作中で確定した事実をまとめた設定台帳。
- **L1:** 文字や設定の機械的検査。**run:** 1回の試行。**seed:** AIへの乱数の指定番号。同じ番号でも同じ文章になる保証はない。
- **manifest／ハッシュ:** どんな条件で実行したかの記録／データの内容を照合するための「指紋」。
- **replay／resume:** 前者は保存した回答を**再生して照合**すること、後者は**途中で止まった仕事を続ける**こと。

**このレポートの判断範囲:** リポジトリ内のファイルと、上記のローカル実行結果をもとにした現状整理です。GitHubの遠隔ブランチ・Releaseの実体、外部のAIや元サイト、第三者の権利許諾については検証していません。
