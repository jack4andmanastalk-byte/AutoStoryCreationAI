# 公開リポジトリと非公開の研究資料を両立する設計案

- 状態: **設計・注意書き**。非公開保管先との自動連携は未実装。公開側の停止・削除状況は
  [保守状況](maintenance_status.md)を参照（最新は 2026-10-29 節）。
- 対象: リポジトリは public のまま、外部作品を本人の研究用に扱う場合。
- 法的な可否を判断したものではない。作品ごとの許諾、サービス規約、利用目的、
  複製・外部送信・加工・再配布の範囲は、原権利者の条件と一次情報を確認する。

## 分離する対象

| 層 | 配置の考え方 | 注意 |
| --- | --- | --- |
| コード、テスト、設定例 | 公開 GitHub | 実作品本文・秘密情報を含めない。テストは架空データを使用。 |
| 出典・書誌・研究結果 | 公開候補 | URL やメタデータでも転載・利用条件を確認する。あらすじ、長い引用、派生文、作品を識別可能な要約は無条件に公開可能とみなさない。 |
| 外部作品の本文、PDF、圧縮・キャッシュ | 本人が管理する**アクセス制限された非公開領域** | 使用・保存・複製の許諾や規約を確認。アクセス権、暗号化、バックアップ、保持期間を管理する。 |
| 生成要求、応答、研究中間物 | 本文を含む可能性があるため原則非公開 | prompt、ログ、トレース、回答、原稿、引用、embeddings や検索索引も内容と権利を確認し、公開用と混ぜない。 |

`.gitignore` は誤コミットの防止策の一つであり、アクセス制御・暗号化・バックアップではない。
GitHub の別ブランチ、公開 Release、公開リポジトリの Actions artifact に置くだけでは
非公開保管の代わりにならない。Arena の作業領域はスナップショット等の保存・アクセス範囲を
別途確認する必要があり、**この文書では非公開の永続保管先だと仮定しない**。

## 候補となる運用

1. 利用者が管理するアクセス制限付きのストレージまたは端末に本文を保持する。利用できる
   連携・ネットワーク・容量・保持期間は未確認であり、このリポジトリだけで提供できると
   主張しない。端末に保存するなら暗号化と別の安全なバックアップを検討する。
2. 研究実行環境に、許可された対象だけを必要な期間に渡す。転送・処理・一時保存が
   作品の許諾と実行環境の規約に適合するかを事前に確認する。外部 AI に渡す場合、
   送信先・保存期間・学習利用等の条件も別途確認する。接続先が使えなければ無理に代替の
   公開保存を使わず、利用可能な環境を決める。
3. 非公開領域内に、作品識別子、出典、取得日、権利者・根拠、許可の範囲、バージョン・
   整合性確認情報を記録する。ダイジェストや識別子も照合や識別に使われ得るため、
   公開可能とは限らない。許諾の証拠やアクセストークンは Git・ログ・チャットに書かない。
4. 公開リポジトリには架空データのテスト、非機密な設定例、必要最小限の再現手順だけを
   置く。研究結果を公開する前には、本文・引用・出力・ログ・メタデータそれぞれの公開可否を
   確認する。AI の出力であること自体は第三者作品と無関係である保証にならない。

接続に使う認証情報は実行環境の承認済みの秘密管理機構に置き、リポジトリや実行ログに
入れない。公開 Actions では secrets やログ出力・artifact の権限に注意し、外部提供者の
認証情報をチャットに貼らない。現時点では非公開ストレージへの接続機能は実装していない。

## 実装前に必要な変更・検証（未実施）

- 公開ジョブと一時成果物を分離する。`publish` だけ止めても `render-narou` の shard
  artifact に本文が含まれるため不十分。自動 schedule、手動 dispatch、artifact、cache、
  Release、`datasets`、ログを一通り対象に、公開経路を網羅して設計する。
- 許諾のないデータを公開側へ送れない fail-closed な境界を設ける。公開可能性は本文だけ
  でなく、メタデータ、あらすじ、派生出力も個別確認する。実際の保存先・アクセス条件を
  決めずに、実装済み・安全と表示しない。
- 現行の `RunLedger.record` は `responses.jsonl` に **prompt と応答を保存**する。
  project の relay、ログ、生成物、resume 用状態も本文を含み得る。private な入力を単に
  gitignore へ置くだけで、既存の「実験成果を GitHub に保存」手順と両立するわけではない。
  永続化先とアクセス制御、再開・バックアップ・監査の方法を合わせて設計する。
- ダミー本文・ダミー認証情報だけで、公開コミット、ログ、artifact、Release、datasets、
  テスト結果に本文が混入しないことと、非公開入力からの処理・再開をテストする。
  本物の著作物・秘密情報をテスト fixture に入れない。
- 個人研究での収集・保存や AI への送信が許されるかは個別の問題であり、公開しなければ
  自動的に許諾済みになるわけではない。

## 既存の公開物をどうするか（本文系は 2026-10-29 に実施・残件あり）

公開済みの Release、Actions artifact、Git 履歴・他者の複製は別々に考える。
必要なら、まず権利と所有者を確認し、安全な非公開バックアップ先と復元方法を確保してから、
対象・範囲・影響を示して明示的な承認を得る。Release の削除、ブランチの強制更新、
履歴書き換えはデータ損失や参照切れを伴う。公開停止後もキャッシュや第三者の複製からの
完全な消去は保証できない。2026-10-29 で本文系の公開物は削除済み（残件: Actions
artifacts、main 履歴上の blob、第三者コピー。[保守状況](maintenance_status.md)）。
