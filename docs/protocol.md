# 評価プロトコル v1.0（凍結）

- 版: `protocol-v1`（凍結日 2026-10-23）
- 対応タスクセット: [`benchmarks/protocol-v1/tasks.yaml`](../benchmarks/protocol-v1/tasks.yaml)
- 状態: **凍結**。本文の変更は §9 の手続きによらなければならない。

## 0. この文書の効力

このリポジトリで「良くなった／悪くなった」「AI 自動創作が機能する」と**言ってよい条件**を定める。
数値だけを貼ることは許すが、**この文書の条件を満たさない比較を結論として扱わない**。

凍結する理由は 2 つある。

1. 結果を見てから基準を変えると、どんな手法も「改善」にできる。
2. スキルを 1 つ足すたびに題材が変わると、効果と題材の差が分離できない。

## 1. 問い

| ID | 問い | 主な測り方 |
| --- | --- | --- |
| RQ1 | AI 単独の生成で、公開作品と比べて遜色のない短編を作れるか | 継続性（L1）、人間のペア比較（L3）、識別可能性（L3） |
| RQ2 | スキル（企画・台帳・文体・改稿）は、どの程度効くか | 条件間の差と分散（L1/L2/L3） |
| RQ3 | 失敗はどの類型に集中するか | チケット分類の分布、CED の内訳 |

RQ2 は「効いた」ことの証明ではなく**効果量の推定**である。効果が 0 という結果も、そのまま報告する。

## 2. タスクセット

`benchmarks/protocol-v1/tasks.yaml` の 10 題を固定して使う。内訳は 幻想 4・現代 3・歴史／神話 3。

各タスクは次の 4 つを持つ。**これ以外の指示は生成側に与えない。**

| フィールド | 役割 | 検査 |
| --- | --- | --- |
| `logline` | 前提（1〜2 文） | — |
| `must_include` | 作品中に必ず現れる語（2〜3） | L1: 文字列一致 |
| `avoid` | 使ってはいけない定型（1〜2） | L1: 禁止パターン |
| `control` | 対照群を選ぶジャンル | — |

題材を追加・変更すると版が上がる（§9）。**10 題で足りないからといって途中で増やさない。**
増やす場合は v2 として、v1 の結果と混ぜずに報告する。

## 3. 生成条件

| 系 | 構成 | 何を測るためか |
| --- | --- | --- |
| **S0** 単発プロンプト | ログライン → 本文（1 回） | 下限。以後の系はすべてこれと比べる |
| **S1** 企画＋本文 | ログライン → canon（台帳）→ 章立て → 本文 | 台帳を持つことの効果 |
| **S2** S1＋改稿 | S1 → 監査 → 修正 → 再監査 | 検査ループの効果 |
| **S3** S2＋文体 | S2 に文体スキルを適用 | 文体層の効果（v1 では任意） |

固定する条件:

* 出力の尺: **3 章・各 1,000〜1,400 字**（合計 3,000〜4,200 字）。
* 試行: **タスク 10 × seed 3 = 30 run／系**。
* 温度・最大トークン・停止条件は系ごとに固定し、`manifest.json` に記録する。
* モデルは差し替え可能とするが、**系をまたいで同じモデル・同じ版**を使う。
  異なるモデルを混ぜた比較は、このプロトコルの対象外とする。

## 4. 測定

3 層を分離する（`skills/evaluation-harness`）。総合点は**作らない**。

| 層 | 指標 | 定義 | 良し悪し |
| --- | --- | --- | --- |
| L1 | `must_include_hit_rate` | 必須語の出現率（全タスク平均） | 高いほど良い |
| L1 | `forbidden_per_10k_chars` | 禁止パターンの密度 | 低いほど良い |
| L1 | `ced_per_10k_chars` | 継続性違反の密度（canon がある系のみ） | 低いほど良い |
| L1 | `chars`, `dialogue_ratio`, `sentence_length_cv`, `mean_paragraph_chars` | 記述統計 | **判定に使わない** |
| L2 | 6 次元（coherence / character / world / originality / orientation / prose） | 1–5、根拠必須 | 次元ごとに報告 |
| L3 | 選好（AI / 人間 / 引き分け） | ブラインドのペア比較 | 勝率（引き分けは 0.5） |
| L3 | 識別 AUC | 「どちらが AI か」の当てやすさ | 0.5 に近いほど良い |
| L3 | 人間間一致（κ） | 評定者 2 名以上 | 報告のみ |

**比較できない組み合わせを比較しない。**

* 監査カバレッジ（マーカーのある章の割合）の差が 30 ポイントを超える CED は比較しない。
* 文字数差が 25% を超えるペアは選好比較に使わない。
* L3 が無い場合、L2 の点数は「較正されていない」と明記する。

## 5. 合格閾値（事前登録）

v1 の判定は次の 5 つ。**すべて満たしたときだけ「機能している（v1 基準）」と言える。**

| # | 判定 | 閾値 | 測り方 |
| --- | --- | --- | --- |
| G1 | 継続性 | high 違反 0 件の run が **80% 以上**（S2） | L1 |
| G2 | 指示追従 | `must_include_hit_rate` が **0.9 以上**、禁止パターン密度が対照群の中央値以下 | L1 |
| G3 | 読者の選好 | 対照群（公開作品）に対する勝率が **0.40 以上**（引き分け 0.5、95% CI の下限が 0.30 以上） | L3 |
| G4 | 識別可能性 | 人間の識別 AUC が **0.70 未満** | L3 |
| G5 | 再現性 | 同一 seed・同一設定で、出力が一致するか差分が説明できる | 実行台帳 |

G3 は「人間に勝つ」ではなく「一方的に負けない」を意味する。0.5 を要求しない。
G5 が満たせない場合、G1–G4 の数値は**参考値**としてのみ扱う。

## 6. 対照群

* 青空文庫の**著作権が消滅した作品**のみを使う（再配布可能）。
* ジャンルは各タスクの `control` に合わせ、**長さを揃える**（3,000〜4,200 字）。
* 1 タスクあたり 3 作品、合計 30 作品を固定リストにする（v1 では選定時に記録し、以後変えない）。
* なろう作品は**ローカル集計のみ**（再配布しない）。対照群として公開比較に使わない。
* 対照群は「お手本」ではなく**ものさし**である。ここから規則を抽出して実装するのは §8 の範囲外。

## 7. 手続き

1. `scripts/run_pipeline.py` で run を作る。出力は `runs/<run_id>/`（git 管理外）。
   `--provider scripted` は配線検証用の台本、`--provider command` が実モデル用。
   鍵を持たない環境では `scripts/chat_operator.py` を `--provider command` の
   コマンドとして渡し、プロンプトを `requests/` に落として応答を `responses/` に
   置く。応答が無いときは **exit 3** で止まり、プロンプトが変わった応答は
   **exit 4（stale）** で拒否する。貼り付けで人の手を経る場合は
   `scripts/relay_prompts.py`（`export` → 回答 → `ingest`）を使う。受け渡しの単位は
   リクエスト 1 件で、タグは run の key を伏せた 4 文字。担い手の版を固定できないため
   G5 は満たさない。
   版を固定できるモデルには `scripts/model_adapter.py`（OpenAI 互換）を使う。
   `--model` と `--model-version` が `manifest.json` に残り、G5 を判定できる。
2. `manifest.json` に次を必ず記録する。
   `run_id`, `task_id`, `system`, `seed`, `model`, `model_version`, `temperature`,
   `prompt_hashes`, `git_commit`, `protocol_version`, `started_at`, `finished_at`, `cost`.
3. L1 は全 run に実行する。L2 は L1 を通過した run にだけ実行する（費用のため）。
4. L3 は層化抽出する（タスク × 系 × 3 ペア、合計 60 ペア以上）。評定者は 2 名以上。
   判定用の束は `scripts/make_blind_pairs.py` で作る（マーカー・見出し・run id を除去、
   文字数差 25% 超は除外、a/b は半々にしてシャッフル）。`key.json` は評定者に渡さない。
5. 結果は `experiments/<id>/results.json` と `note.md` に置く（`experiments/README.md` の規約、`run_experiment.py` の既定出力）。`note.md` には
   **仮説・条件・N・結果・限界**を書く。生の run 出力はコミットしない。
6. 集計は `scripts/summarize_experiment.py` で行い、平均だけでなく 95% CI と N を出す。

## 8. 報告規則

* **総合点を出さない。** 次元・指標ごとに報告する。
* 有意差と言うときは CI を添える。N を書かずに「改善した」と書かない。
* 効果が無かった条件も表に残す（選択的報告をしない）。
* 単一作品・単一 seed の結果を傾向として一般化しない。
* ベンチマークの外部スコアを目的化しない。比較は同一プロトコル内に限る。
* 「機能している」と言えるのは G1–G5 を満たしたときだけ。それ以外は
  「v1 の範囲では G3 が未達」のように、**どの条件が未達か**を書く。
* 生成物の著作権・利用条件は `docs/legal_and_ethics.md` に従う。

## 9. 版の上げ方

次のいずれかを行ったら **v2** とする。v1 の結果と混ぜて集計しない。

* タスクセットの追加・変更・削除
* 系（S0–S3）の構成変更
* 指標の定義変更、閾値の変更
* 対照群の入れ替え

スキルの追加・改良、プロンプトの改善、モデルの更新は**版を上げない**（それが測る対象）。
ただしモデルを変えた比較は、同一モデル内の比較と分けて報告する。
