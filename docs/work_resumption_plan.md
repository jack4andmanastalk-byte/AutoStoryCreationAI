# リポジトリの現状に基づく作業再開プラン

## 目的と現在地

目的は、AIが題材と制約から世界・人物・構成・本文を作り、検査と修復を経て、続き・改訂・編纂を行えるよう実用性を高めること。標準入口は [`scripts/story_project.py`](../scripts/story_project.py) であり、[標準フロー](standard_flow.md)と[実用改善ロードマップ](practical_roadmap.md)が採用済みである。`run_twostage.py` は実験用で、標準入口ではない。

既に行われたこと:

- [dogfood-01](../experiments/2026-10-dogfood-01/note.md): 3章生成、改訂、4章への追加、子作品と共有 world の編纂を実応答で実施。
- [dogfood-02](../experiments/2026-10-dogfood-02/note.md) と [dogfood-03](../experiments/2026-10-dogfood-03/note.md): 字数許容幅と carried 設計書の履歴を改善し、dogfood-03 の4章で確認。後者の記録には F-44、F-46、F-47 の具体的な摩擦が残る。
- [Stage A 1.1 実走](../experiments/2026-10-stage-a-v11-t01/note.md): 実験経路で Stage A → B が完了。ただし救済の分岐や持ち越しの本文反映は、この1回だけで実証されていない。
- 実走中断への対策として、保存先チェックと GitHub への checkpoint 手順を追加済み（[調査記録](incident_analysis_2026-10-28.md)）。

したがって、標準入口の選定や初回 dogfood を一からやり直すのではなく、**既存の実走で見つかった摩擦を確認・改善する**ところから再開する。

## 優先順

### 1. 標準フローの保存・復元を確認する（P0）

- 既存作品を上書きせず、テスト用 project を使い、`works/<project-id>` の `project.json`・`nodes/`・`relay/`・**project 内 `runs/`** を含む必要な状態を Git に保存する。
- Git の別チェックアウトから `status` / `doctor` と応答待ちの再開を確認する。保存済み応答を重複生成・上書きしないことも確認する。現在の二段階方式の checkpoint テストだけで標準フローの復元を検証済みとは扱わない。
- `scripts/check_persistent_paths.py` は保存先の検査に使えるが、GitHubへの push や project 全体の復元可能性を保証しない。`experiments/README.md` の run 保存方針と現行の project 内 `runs/` の追跡実態に差があるため、実際の復元検証を基に説明を整える。
- **完了条件:** 新しいテストが通り、必要なファイルと復元手順が明文化される。大きなデータや秘密情報は無条件に通常ブランチへ保存しない。

#### 復元テストの追加（2026-10-28）

- 標準フローで plan 応答と design 待機を Git に保存し、別 checkout に clone、
  元の checkout を削除してから `status` / `doctor` / `resume` を経て3章まで完走した。
  保存済み応答が上書きされないことも確認した。応答は固定台本であり、実モデルの
  再現性や品質の証拠ではない。
- チェックポイントに project 相対パスを記録し、旧チェックポイントは既定の Arena relay
  のみ移動先へ解決する。外部 operator と旧版カスタム relay は自動移動しない。
- [標準フロー](standard_flow.md)と[実験の保存規約](../experiments/README.md)を同期した。

### 2. dogfood-03 の具体的な摩擦を小さく解消する（P1）

1. **F-47:** `summary` の「設計の累計」がリビジョン内の集計であることを表示で明確にする。対象は `src/asc/project/summary.py` とその表示テスト。集計値の意味や過去の成果物は変更しない。
2. **F-44:** `brief` の `logline_elements` の逐語一致が1回の修復を生んだ事例を確認。まず既存の checker と prompt を調べ、依頼文の明確化を優先して検討する。検査を緩める場合は見逃し・誤検出を回帰例で検証する。
3. **F-46:** `continue` 後の plot の acts / scene の新章網羅が、現行 checker でどこまで検査されるかをコードとテストで確認する。欠ける場合のみ再現例を追加し、必要な契約・検査を設計する。

**完了条件:** 各項目について、現行挙動・変更理由・回帰テスト・残る制限を記録し、実装した変更について関連テストを通す。未確認の問題を修正済みと報告しない。

### 3. 修正後の実用確認（P1）

- 利用者の開始指示と題材・制約を受け、標準フローで新しい作品を生成する。既存 dogfood の出力・応答を変更せず、新しい project ID を使う。
- `init` → `run` → `relay status` / `relay submit`、完了後に `doctor`・`summary`・`render --reader` を使う。エージェントは実際に生成した応答だけを relay に記録し、捏造しない。
- 応答待ち・取り込み・完了の各節目で、必要な状態・要求・応答を点検し、現在の作業ブランチへ commit / push する。push に失敗したら保存できたと報告しない。
- **完了条件:** 読書用原稿、状態と検査の要約、実際の摩擦と読後所見を残す。`clean` は品質の保証ではなく、1作品の観察を率や因果効果として扱わない。

## 実験経路の位置づけ

Stage A 1.1 の追加確認は標準フロー改善とは別の実験として扱う。実施する場合は既存 run1 を変更せず、新しい run で `fail_forward` / `rescue` や `carry_forward` の実際の扱いを確認し、結果と応答の出所を記録する。[runbook](../experiments/2026-10-stage-a-v11-t01/runbook.md)を参照。L2/L3 は凍結中で、実験の `clean` を物語の質やモデル再現性の証拠にはしない。

## 作業開始の単位

P0 の標準フロー保存・復元テストを実施済み。次に F-47 → F-44 → F-46 の順で調査・小さな修正を進める。新しい実作品を生成する段階では、題材と制約について利用者の指定を受ける。
